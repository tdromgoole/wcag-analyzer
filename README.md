# Access Lens

A local accessibility inspection extension inspired by the supplied WAVE screenshot, with an independent interface and axe-core scan engine. Supports Chrome and Microsoft Edge (Manifest V3).

## Install

1. Run `npm ci` and `npm run build`.
2. Open `chrome://extensions` or `edge://extensions` and enable **Developer mode**.
3. Choose **Load unpacked** and select `dist/access-lens` inside this project.
4. Open a website and click the extension's toolbar button. Pin the extension for easier access.

Click a category to browse checks, expand a rule, and click an element to scroll to and highlight it. Red markers identify issues; amber markers identify checks needing review. Toggle markers off to inspect the page without annotations. Click **Scan page** after changing the page or opening a menu. Click **Export JSON** to download the latest completed scan. Clicking the toolbar button again closes the inspector.

The panel overlays the left 380 pixels of the page; it does not reflow the site. Close it to interact with content underneath it.

During both scan passes the inspector is hidden, numbered markers and highlights are physically detached from its shadow DOM, and annotation redraws are blocked. The annotations are restored after success or failure. This prevents Access Lens overlays from causing false “background color could not be determined” contrast reviews. You can leave **Page markers** enabled when rescanning.

The compact panel keeps findings in their own main scroll area. Use the **View** dropdown to switch between Details, Reference, Order, Structure, Contrast, Changes, Manual, Sitemap, and Site report. **Scan & save details** expands to show the page/engine metadata, full save filename and time, page state selector, scan scope, and browsing pause control. Save/queue status remains on its collapsed summary, and retry actions stay visible when needed. Report explanations and sitemap legends are expandable within their views.

## Save settings

History preservation retains completed scan and review snapshots locally in both folder and browser-download modes, including when disk auto-save and Remember history are off. It runs before a browser download is authorized or a current folder report is replaced. Settings → Export preserved evidence JSON downloads locally staged snapshots without removing them. This store is separate from Remember history and is limited to 100 snapshots or 20 MiB; reaching capacity blocks new saves/download authorization visibly rather than evicting evidence. Choose a folder and archive staged evidence to recover capacity; export or archive important evidence before clearing browser extension data or uninstalling. Settings → Archive preserved evidence to selected folder writes content-addressed JSON under `access-lens-history`, verifies each copy, then releases its local staging space. Identical retries reuse archived files; conflicting nonempty files are not overwritten. Archive files remain in the folder, and subsequent exports include only snapshots still staged locally. Portable bundles include a versioned evidence-event ledger with stable snapshot/event IDs, scan IDs, outcomes and original review timestamps. Unknown attribution remains null. This records preserved scan/review evidence; future source-change, remediation and auditor-attribution features remain separate. Folder replacement now preserves the validated previous disk report and final merged review state before writing; failed preservation blocks replacement. Supported legacy copies are normalized before staging/export: verbatim image alternatives are removed while findings, locators and reviews remain. Original disk artifacts and already-written archives are not rewritten. Raw content fields or unsupported report roots stop the operation visibly rather than being exported. Native folder permissions and independent writers still require care; browser-local locks cannot protect another developer's filesystem writes.

Page review choices are saved in each page/state report: WCAG criterion decisions, the general manual checklist, and the assessment of a recorded keyboard run. Choose a save folder in Settings. Changing a checklist decision or keyboard assessment updates that JSON immediately, even when **Automatically save after each successful scan** is off. Failed writes use the recovery queue. Without a selected folder, use **Export JSON** after making choices.

When opening the inspector again, the extension reads the matching JSON from that selected folder and restores earlier decisions, independently of **Remember history**. Page states have separate files. Restored choices retain their original review times; a fresh scan may require revalidation. Newer locally remembered or queued checklist decisions take precedence. Missing files start a new review; unreadable or invalid JSON stops the scan before the existing report can be replaced. Restore folder access or repair the file and scan again. Browser downloads alone cannot be read back automatically; select their folder in Settings to allow reading.

Click **Settings** in the inspector (or the extension's Options entry) and **Choose folder…** to select a JSON destination. This opens the browser's folder picker and requests write access to that folder. Manual exports then save directly there. **Automatically save after each successful scan** is off by default; when enabled, it saves the opening scan and every successful rescan. Settings apply across sites. Each page gets a stable filename derived from a SHA-256 hash of its protocol, host (including port), and path. Rescanning the same page replaces its JSON in the selected folder. Different paths or sites get different files. Query strings and fragments are ignored by default; selected route identity can be enabled in Settings. Exports include pagePath (protocol, host, and pathname); query strings, fragments, and embedded credentials are excluded. Browser downloads use the same suggested name, but the browser may add a numbered suffix rather than replace an existing download.

**Use browser downloads** clears the selected folder and disables auto save. Manual exports then use the browser's normal download location and prompts. If folder access expires, restore access in Settings. Folder-save failures are queued and appear in the inspector with a retry action. A successful folder save shows its time and filename; browser downloads show the request time because completion must be checked in the browser. Raw axe results are never stored in extension storage; the recovery queue temporarily retains content-free reports, including pagePath.

Settings shows whether write access is currently granted. Use **Restore folder access** to grant access again, then return to the inspector and click **Retry save**. If access expires when Settings closes, keep that tab open while saving. Errors distinguish expired permissions, missing folders, locked/read-only files, storage limits, and outdated report filenames without revealing native file paths. Unknown errors retain a generic recovery message rather than guessing the cause.

## Automatic browsing scans

In Settings, select a writable save folder, enter a website address under **Automatic browsing scans**, and click **Enable for this site**. Approve the browser's optional site-access request. This registers a top-level background scanner for that protocol/hostname, including future visits and matching pages already open, without displaying the inspector. Host permissions apply across paths and ports; subdomains and HTTP/HTTPS are enabled separately. Enabled sites remain configured across browser sessions until **Disable** is clicked. Site match patterns are browser extension configuration; no page paths, query strings, page text, or raw results are retained in that configuration.

Browsing mode saves independently of the inspector's auto-save checkbox. It detects full page loads, changes to the browser address (including SPA navigation), selected tabs, expanded controls, and open dialogs/details. It waits briefly for DOM activity to settle, with a six-second settling limit on busy pages. Pages visited too briefly, continuous loading, iframe content, and late updates without navigation/state changes may not be captured. Wait for the toolbar **OK** badge before leaving a page when you need to ensure it was saved. **SCAN** means a scan is running; **Q** means a report is queued locally, **P** means paused, **SKIP** means excluded, and **!** means it failed. Hover over the extension toolbar button for its recovery message. The Settings page also shows the last browsing-scan result.

Reports use the same content-free format and stable page/state filenames, update the sitemap, and use optional saved comparison/checklist history when enabled. No panel is opened and no linked pages are fetched automatically. An open inspector temporarily pauses background scanning in that document to avoid overlapping scans. Scan failures retry twice. Completed reports with failed file saves enter the recovery queue and do not require revisiting the page. Visits that never completed a scan must still be revisited. Restoring folder access or choosing a folder retries queued saves and retriggers scans in open enabled pages. Keep Settings open if the browser revokes folder access when that tab closes. Disabling a site stops its scanner and removes its optional host permission; existing files and queued reports remain.

Enabled browsing sites are saved independently of Chrome's dynamic script registrations. The worker restores missing registrations after reloads and browser restarts using existing site permissions, and restarts scanners in matching open tabs. Upgrades recover exact-site permissions granted by earlier versions. Revoked permissions are not requested automatically; Settings shows a restoration error. Disabling a site removes its saved configuration so it stays disabled after restart.

## Coverage, recovery, and scan controls

The **Sitemap** coverage summary counts discovered pages, scanned/unscanned pages, failed/interrupted attempts, queued saves, exclusions, stale results, limited scans, and the most recent scan. These counts overlap: a scanned page can also have a queued save or an old failed state. Groups inferred only from URL paths are not counted as discovered pages. Pagehide interruption reports are best effort; a recorded scan attempt still unfinished after two minutes is treated as interrupted. This is recorded coverage, not a guarantee that every browser visit was captured.

Folder saves use a write-ahead **Save recovery queue** in local extension storage. It holds the latest content-free report per filename across browser and worker restarts, up to 100 reports or approximately 20 MB of serialized report/metadata text. A full queue rejects new entries visibly rather than silently evicting reports. Older scan snapshots cannot replace newer pending snapshots. Successful saves remove their pending entry; failures retry about once a minute, on folder restoration, or via **Retry queued saves**. Browser scheduling may delay retries. **Delete queued report** and **Delete all queued reports** remove pending data without deleting files already saved. A write already in progress may finish. Queue data includes the explicitly requested pagePath, so paths can contain sensitive identifiers even though element content is excluded. Browser-managed downloads cannot be queued on failure because their completion is not observable by the download link.

Pause background scans and automatic retries from **Settings → Coverage and scan controls**, the panel's **Pause browsing scans** button, or the extension toolbar's right-click **Pause background scans** menu. Explicit manual scans and explicit queue retries remain available. **Excluded paths** apply across all sites to manual/browsing scans and queue retries. Enter one exact pathname per line or a prefix ending in `*`; no query strings or fragments. Both literal and decoded path forms are checked. Exclusions do not delete previous files or queued data. Remove an exclusion or delete an excluded pending report to resolve it.

Configure **query parameter names** and **URL fragment routes** to distinguish application screens that share a pathname. Only selected route values affect hashed page identity and filenames; their values are not exported as text. pagePath remains protocol/host/path only. These controls apply to manual and automatic scans, sitemap identity, comparisons, and save filenames. Configuration changes create new records; old records remain. By default, query strings and fragments are ignored.

Results become **stale** after seven days by default; change this to 1–365 days in Settings. Sitemap clean results become amber when stale, incomplete in scope, or affected by scan/save gaps. Manual results that are old or predate the latest scan are marked for revalidation; **Revalidate** records a new review time for the current result. A green check always describes recorded automated results within scope, never full conformance.

## Site-wide report

Version 1.9.0 adds a folder-based site review for the scan → AI fixes → rescan → manual review workflow:

1. Choose your report folder in **Settings**. Save each page and important page state there while scanning your application.
2. Give the page JSON to your AI coding tool, make fixes, then rescan and save. The new automated scan is the current evidence; a missing issue means “no longer detected,” not proof of a fix.
3. Record manual decisions in **View → Manual**, or edit the corresponding `manualChecks` entries in the page JSON. Each entry needs a supported `status` (`pass`, `fail`, `not-applicable`, or `not-tested`) and an ISO `checkedAt` date recording when it was actually reviewed. Scope checks require Pass or Fail. Keep the file's name, page identity, state key, and scan timestamp unchanged when editing manual decisions. Updating a decision without updating its review time does not make it a fresh review.
4. Open **View → Site report** on any page of that site. The extension reads the selected folder and uses the latest saved scan for each page state, including browser download copies named `access-lens-<hash> (1).json`. Click **Refresh report from folder** after external edits or new saves.
5. Use **Export site report JSON** for further analysis or **Export site report HTML** for a readable, standalone report that can be shared or printed.

The report separates automated issues and checks needing review, manual Pass/Fail/Not applicable/Not tested decisions, review dates and revalidation needs, stale or limited scans, recorded keyboard assessments, and known pages without saved reports. It groups recurring rules and structural patterns as possible shared fixes. It recalculates coverage from the evidence rather than trusting a precomputed `wcagCoverage` in the files. It does not assign a compliance percentage or certify conformance.

Only current-site reports in the selected folder's top level are included. Other sites and unrelated files are ignored. Reads are limited to 2,000 matching files, 20 MB per file, and 100 MB total per refresh. Invalid, unreadable, oversized files and reached limits are counted visibly and mark the result partial. Pending recovery-queue reports are counted separately; retry saving them before generating a final report. Known unscanned pages come from the local sitemap, not a site-wide crawl; unvisited pages and states remain unknown. Legacy reports without a hashed page identity group by path, so configured query/fragment routes should be rescanned with the updated extension to get distinct page identities.

Site report exports include sanitized page paths, hashed state filenames, manual decisions, and review metadata. Page content, alternative text, query strings, and fragment values are omitted. This is broader than the old local-history summary, which remains available and labeled when the folder report cannot be loaded.

Before replacing a page report, the extension rereads its saved JSON and merges the latest dated manual decisions. Newer disk decisions win over an older open inspector; the returned choices update the panel after saving. Earlier decisions keep their review times and may need revalidation after a new scan. A newer saved scan, mismatched page/state identity, malformed JSON, or invalid manual decision blocks replacement and leaves the attempted save queued. Resolve the conflict or rescan before retrying. Avoid editing a file at the same time another application is writing it.

## Modals, tabs, and scan completeness

Opening a native dialog, a visible element with dialog/alertdialog semantics, selecting an ARIA tab, or expanding a recognized control triggers a separate browsing-mode state scan after settling. Navigate through each modal and tab yourself; the scanner never clicks controls, submits forms, or opens hidden panels automatically. Custom widgets without detectable semantics may require a manual scan and a numbered state slot. Focus entry/return, traps, Escape behavior, and screen-reader usability require the manual checklist.

Every page JSON contains **completeness** with completed-scope status, duration, excluded frame counts, hidden tab-panel counts, and supported open shadow-root counts. Automatic scans also record whether the DOM settled first or changed during the scan. Excluded frames or hidden panels make the scan limited in scope. Closed shadow roots cannot be detected reliably, so the report explicitly records that limitation instead of claiming zero. If a tab embeds another page through an iframe, its contents are excluded even when same-origin; open that page directly to scan it. Hidden tab content must be activated before it can be evaluated. Scan failures/interruption appear in coverage instead of producing a falsely completed report.

Axe may fail to preload stylesheet/media assets that a site blocks or cannot load. Scanning continues with the available data and existing checks. The extension captures axe's specific nonfatal preload warnings as structured completeness diagnostics, marks the scan limited, and shows the explanation in **Scan & save details**. Raw events, error messages, and asset URLs are not exported; unrelated warnings are unchanged. This does not bypass site restrictions or turn unavailable checks into passes. After reloading/updating the extension, refresh existing webpages: obsolete background scripts stop cleanly, and obsolete inspectors ask you to refresh before scanning or saving again.

## Changes, guidance, and manual testing

### Additional automated evidence

Version 1.8.0 adds **View → Additional checks**. Seven supplementary checks run with manual and automatic browsing scans: content outside the current viewport, clipping of text-bearing containers, positive tab order values, video without caption/subtitle tracks, autoplay media without native controls, email/telephone fields without expected purpose metadata, and long-running CSS animation configurations. Findings include structural locators and fixed numerical/boolean measurements; page text, names, values, raw HTML, CSS IDs/classes, and animation names are excluded. Click a candidate to locate it on the page. `supplementalChecks` in JSON contains these measurements, viewport dimensions, timestamps, and scope limits. Scans examine up to 5,000 elements in the document and supported open shadow roots, with 100 observations per check; reaching a limit is explicit.

**Run text-spacing stress test** temporarily applies line height 1.5, paragraph spacing 2em, letter spacing .12em, and word spacing .16em; measures new or increased geometric clipping; then restores the original inline styles and scroll position. Cleanup also runs after interruption and preserves unrelated live changes made by page scripts. No controls are activated. The stress test runs on demand, separately from normal scans; its latest result is saved in `textSpacingTest` and included in JSON/auto save. This result stays with the current scan; rescanning creates fresh evidence and requires rerunning this stress test.

These are review candidates, not confirmed violations or whole-criterion passes. Autoplay may be blocked/short/muted or have custom controls; video may have no audio or use external captions; fields may collect another person's details; animations may not convey moving information; positive tab order and clipping can need contextual interpretation. Overflow at the current viewport is not a 320 CSS pixel reflow test. Caption accuracy, custom controls, visual overlap, hidden states, language exceptions, frames, and closed shadow roots still need evaluation. New supplemental or text-spacing evidence makes earlier affected criterion assessments require revalidation. The coverage checklist links each criterion to its supplementary evidence. No new browser permission is required.

### Recorded keyboard traversal

#### First-time setup and starting a test

1. Open Access Lens **Settings → Automated keyboard testing** and click **Enable keyboard testing**. This is off by default. Confirm that the status says testing is enabled.
2. If the browser disabled the extension after an update, open `chrome://extensions` or `edge://extensions`, review the requested permissions, and re-enable Access Lens. Keyboard testing requires the debugger permission included with installation.
3. Close DevTools and other debuggers. Return to the webpage and refresh it if Access Lens was updated or reloaded, then open the inspector.
4. Choose **View → Keyboard test**, set the steps, and click **Run keyboard test**.
5. Wait for the browser's debugging banner. Leave it open and click **Begin traversal** in the webpage. Clicking Cancel on the banner stops the test. Keep the tab active and avoid typing during the run.

Press **Escape** or **Stop keyboard test** to stop early. To keep the transcript on disk, choose a writable folder and enable automatic saving, or click **Export JSON** after the run.

After clicking **Run keyboard test**, wait for Chrome's debugging banner, then click **Begin traversal** in the webpage. This returns focus to the page before any Tab is sent. Leave the banner open during the run: canceling it disconnects the driver and stops testing. Startup focus loss sends no Tab presses; interruption details distinguish a canceled debugger from focus leaving the page. Switching tabs, navigation, embedded frames, and Escape still stop the test.

Version 1.8.1 adds a numbered path on the page when **View → Keyboard test** is selected. Arrows join consecutive recorded focus stops; numbers match the transcript's actual step numbers. Forward Tab uses solid blue arrows, and Shift+Tab uses dashed arrows with purple numbers. Choose forward, reverse, or both directions, or hide the path. Numbers select and highlight the corresponding transcript entry. Positions are recalculated on scrolling/resizing from the current DOM, rather than the historical coordinates; missing/hidden elements break the path. Initial document focus and browser-boundary entries are not drawn. Repeated visits to one element keep their separate step numbers. The existing **Page markers** switch also hides the path.

**Human assessment of this keyboard run** offers Not reviewed, Pass, and Fail. The timestamped assessment belongs to that run ID, is exported in `keyboardTest.assessment`, and is retained with the latest local recovery transcript. A new run starts unreviewed. Fail counts as a manual failure in sitemap/site reports; Pass does not fill in the separate WCAG criterion checklist. An unreviewed or stale run prevents review completion, and a previous scan's assessment needs a fresh run. Automatic browsing scans retain the last matching transcript as earlier evidence rather than discarding a recorded failure. Assessments of an interrupted test cover its recorded steps only; untested interactions and complete tasks still require review.

Version 1.7.0 adds **View → Keyboard test**. First turn on **Settings → Automated keyboard testing → Enable keyboard testing** (off by default). The extension declares Chrome's `debugger` permission at installation because Chrome cannot request this permission optionally. An update may require accepting the new permission or reinstalling the extension. Chrome displays a debugging banner while the test is attached; close DevTools and other debuggers before starting. The driver attaches only when a user starts a run, accepts only Tab/Shift+Tab commands for that initiating tab/document, and detaches afterward. Disabling testing in Settings stops an active run.

Choose 1–100 steps per direction (default 20). The inspector temporarily hides and leaves the tab sequence. The test focuses the document start, sends real browser Tab presses, then Shift+Tab presses if the forward segment finishes. Keep the tab active and do not type during a run. **Escape** or the floating **Stop keyboard test** button interrupts it. Focus leaving the page, entering an embedded frame, navigation, driver disconnection, or a 90-second limit also stops it. A short page can reach browser chrome before the reverse segment; its transcript records that interruption rather than claiming a completed test. Controls are never activated: Enter, Space, arrow-key widget behavior, form submission, dialog opening/closing, and complete tasks require separate testing. Prepare dialogs or other states yourself and scan/test each state.

The on-screen transcript and page JSON's `keyboardTest` record every sampled step: key/direction, elapsed time, structural focus locator, element rectangle, basic outline/shadow evidence, and possible visibility flags. Click a transcript entry to locate it on the current page. Repeated focus, a covered center point, or an absent outline are evidence for human investigation, not confirmed failures. Successful traversal never automatically passes a WCAG criterion. `wcagCoverage.keyboardEvidence` points reviewers to the run and related criteria. There is no screenshot/video capture or collection of page text, accessible names, CSS IDs/classes, typed values, or raw HTML in this transcript.

The latest run is checkpointed locally after every observation so partial results survive navigation and browser/worker restarts. Only one latest transcript is retained, associated with its hashed page-state filename; a later run replaces it. Scan the same state to recover it; a transcript from an earlier scan is clearly labeled. Use **Export JSON** to keep the transcript with the report (or enable folder auto save). Settings can delete the last local transcript; already exported files and an active run are unaffected. Browser-native installation permission, debugger attachment/banner behavior, and operating-system/browser-chrome focus need a manual browser check. Automated tests exercise real Chrome key dispatch and the extension UI with a mocked extension API boundary, plus worker lifecycle/error handling.

### WCAG 2.2 AA coverage

Version 1.6.0 adds **View → WCAG coverage & manual** with all 55 active Level A/AA success criteria (31 A, 24 AA). The catalog follows the [W3C WCAG 2.2 Recommendation](https://www.w3.org/TR/WCAG22/); obsolete criterion 4.1.1 is excluded. Each criterion includes a test prompt, normative reference and exceptions link, applicable automated rule results, and a separate human assessment. Prompts are starting points; consult the normative requirement and its exceptions when evaluating. Existing six general checks supplement this catalog; they do not fill in criterion results automatically.

Automated passes never mark a whole criterion as passed. Every criterion starts untested and requires an explicit Pass, Fail, or Not applicable assessment. A detected violation remains a failure even if a human assessment says Pass. Incomplete automated results require review; recording a human Pass or Not applicable resolves that review, subject to failures and scope gaps. Earlier assessments require revalidation after a rescan or the configured stale interval. Page-state history remains opt-in through the existing history setting.

Five additional scope reviews cover full pages/states (including excluded embedded content), complete processes, accessibility-supported technologies, non-interference, and the page set. All require Pass before recorded review is complete. Limited automated scope blocks criterion completion until a current full-page review is recorded. These are reviewer attestations, not additional automated tests: embedded frames, closed shadow roots, unvisited states, media, and complete user journeys still need separate evaluation.

Page JSON now includes `wcagCoverage`, containing all criterion statuses, mapped automated rule IDs by result bucket, manual assessments/timestamps, scope reviews, counts, and `reviewComplete`. `conformanceEstablished` remains false: a recorded review is not an independently verified conformance claim. Automatic browsing scans export this coverage too. The sitemap stays amber when WCAG review is incomplete; older states without coverage metadata also need review. Previously recorded historical `complianceAt` dates remain historical and do not prove conformance.

**Changes** compares the latest scan with the prior scan of the same page state. It lists new violations, violations still present, and violations no longer detected. Matching uses rule IDs and structural locators; moving DOM elements can look like new/resolved findings. A finding that disappears is not proof of a fix, and untested areas may still have problems. Only violations are compared, not the informational inventory or checks needing review.

Each rule includes suggested repair and verification guidance. Common rules include code examples; other rules direct you to inspect semantics and interaction using the linked rule reference. Examples need adaptation to the page. Content decisions still require human judgment.

**Manual** records Not tested, Pass, Fail, or Not applicable for keyboard navigation, visible focus, dialogs/menus, zoom/reflow, screen-reader behavior, and content review. Each result includes a review timestamp in the JSON. Results are self-reported and may become stale after changes. With a selected folder, changing a checklist decision saves it immediately; otherwise export again to update the file.

Comparison and checklist data stay in inspector memory by default. Enable **Remember content-free comparison history and checklist across sessions** in Settings to keep a compact latest-issue baseline and checklist per page state in local extension storage. No raw page text or addresses are stored. Disabling this preference clears saved history. **Clear comparison history and checklists** removes stored history without changing the preference; reopen existing inspectors to clear their in-memory data.

## Page states and diagnostic context

Filenames incorporate a hashed page-state signature in addition to site/path and optional configured route identity. Visible dialogs, selected ARIA tabs, and expanded controls contribute structural state information, never their text or IDs. Rescans of the same state overwrite its file; different states have separate files and comparisons. Use **Page state slot** to distinguish screens automatic detection cannot identify. Slots are numbered to avoid saving sensitive names. Identity configuration changes can create new filenames alongside earlier files.

Content-free diagnostics include recognized explicit ARIA roles, structural parent/label relationships, reference presence/count/validity, safe ARIA states, focusability, disabled state, and numeric element/font/outline measurements. References resolve within their DOM or shadow root; validity indicates that referenced IDs exist, not that their meaning is correct. No referenced IDs, label text, attribute content, or computed accessible names are exported.

## Sitemap

**Sitemap** builds a path hierarchy from the current page and up to 200 same-origin page links per refresh. It grows as you visit and scan pages; it does not fetch or scan linked pages automatically and is not a complete site crawl. External sites are excluded; query/hash route identities can be enabled in Settings. Intermediate paths are shown as path groups unless discovered as actual links/pages.

- Red **×**: at least one scanned state has detected violations or a manual checklist failure.
- Green **✓**: all recorded scanned states have zero detected violations, zero manual failures, and zero checks needing review. Unscanned states and unperformed manual checks are not covered; green is not WCAG conformance.
- Amber **!**: no detected violations/manual failures, but checks need review, results are stale, scope is limited, manual results need revalidation, or scan/save gaps remain.
- Gray **?**: the page/path has not been scanned.

Rescan each affected state after a repair to update its status. A clean state does not erase another state's unresolved issues. Expand **State scan details** for counts and the last-update time. Status reflects recorded scans, not live monitoring. **Refresh sitemap** discovers links and loads the latest statuses; **Clear sitemap** resets this site's recorded map and rediscovers current links as unscanned.

The sitemap persists locally across pages and browser sessions, independently of optional comparison history. Each node retains its readable pathname, including the page name (for example, `/guides/page-name.html`), alongside hashed keys/relationships, discovery flags, rule counts, rule/locator fingerprints, completeness flags, attempt statuses, and timestamps. `sitemap.json` includes this `path` field. Query strings, fragments, credentials, page titles, link text, and element content are excluded. Stored paths also let the sidebar show pages discovered on previous visits. Older hash-only entries receive paths when rediscovered; until then their exported path is null. Paths can contain sensitive identifiers. Storage is capped at 2,000 path entries per site. Sitemap data is shown in the tab, not added to individual-page JSON exports.

Each sitemap entry includes `dateAdded`, an ISO 8601 UTC timestamp set when the entry is first recorded. Rediscovery, rescans, and save retries preserve it. Older entries without a recorded addition date export `null` until rediscovered, when tracking begins; their original discovery time cannot be recovered. Clearing the sitemap resets addition dates.

## Inspection views

Features, Structure, and ARIA show informational inventories with a clickable icon for every element. Group checkboxes control page markers. Structure includes headings, lists, landmarks and tables. ARIA includes attributes/roles, labels and hidden attributes. These counts are observations, not passed checks; hidden elements are included in inventories.

Details shows the selected category. Reference provides rule descriptions and element snippets. Order estimates sequential keyboard focus order; custom widgets, shadow DOM and browser behavior require manual verification. Inconclusive checks are labeled “Unable to determine automatically — manual review required” and do not use the engine's “Fix any of the following” wording. An image-backed button can need contrast review without a detected contrast failure. Contrast separates detected text-contrast failures from checks requiring manual review, with measured ratios, required thresholds, and available foreground/background colors. Gradients, images, identical colors, and empty inputs can require human review; placeholders and non-text contrast require separate evaluation. A clean automated result is not complete contrast coverage. JSON schema 2.0 includes content-free inventories and filtered axe results.

## Contrast regression fix in 1.12.0

Ancestor pseudo-elements (including clearfix whitespace and decorative icons) remain in the captured background and no longer block automatic contrast measurements. Generated text on the measured element itself still requires separate handling. Unresolved results distinguish active animations, unsupported native-input geometry, and generated text.

## Automatic stability retry in 1.12.0

If text position, line wrapping, or CSS changes during automatic contrast capture, Access Lens restores the page and retries once after a brief settling interval. A second unstable capture remains unresolved. Reports distinguish element removal, inline-style changes, computed-style/animation changes, text-layout changes, and blocked text hiding instead of using one generic page-changed explanation. A manual single-pixel measurement remains evidence for that color pair, not for every background point across the text.

## Page traversal for contrast in 1.12.0

Explicit inspector scans now visit unresolved off-screen contrast candidates automatically. This closes the earlier viewport-only gap that left review markers on text encountered later while scrolling. The scan visits up to 12 viewport positions or approximately 15 seconds, measures supported text, and restores the original page and nested-container scroll offsets. User scrolling, pointer/key input, navigation, or losing visibility stops traversal; user interruption preserves the user's current scroll position. Limits and capture failures leave reviews unresolved, never silently passed. The Contrast view and JSON contrastAnalysis show traversal status and viewport counts. Background browsing scans never scroll the page; an explicit inspector scan can traverse even when browsing mode is also configured. Lazy-loaded content and changes triggered by scrolling can still require rescanning.

## Contrast diagnostics in 1.12.0

Expand **Contrast debug** beneath a contrast element in Details, Contrast, or Passed checks. It shows the CSS foreground source, required ratio, screenshot scale, measured line-region sizes, minimum/maximum ratios, pixel counts below the threshold, and the split between a two-CSS-pixel region-edge band and the interior. The eight most frequent sampled colors and up to eight worst distinct-color samples include color, ratio, line-region number, and device-pixel coordinates within that region. Top-color counts are a bounded summary, not the full histogram.

A small local background-only preview marks worst sampled points in magenta. CSS text and its shadow were hidden for this capture; text embedded in raster images remains. This is line-rectangle background analysis, not glyph detection or OCR. Proximity to a region edge does not establish antialiasing, and no edge pixels are discarded. Classification and thresholds are unchanged. Unresolved mixed-background measurements retain diagnostics too; engine-only or unmeasured results explicitly say no Access Lens pixels were measured.

**Export JSON** includes allowlisted contrastDebug numeric/color evidence on each measured check. The preview stays in inspector memory and is never saved, queued, or exported. Reproduce a questionable scan, open its Contrast debug panel, and export JSON to retain the measurement evidence.

## Fractional-boundary sampling fix in 1.12.0

Automatic contrast now samples only complete device pixels inside each CSS text rectangle. Earlier outward floor/ceil rounding could include adjacent image or icon colors in the last fractional column/row, as the supplied Security-link diagnostics demonstrated. This is not blanket removal of a one- or two-pixel border: low-contrast pixels wholly inside the text region still count. Too-small regions without a complete pixel remain unresolved. Diagnostics record samplingBounds and each region's CSS insets for reproducing the measurement.

A later viewport that cannot measure a previously tested result no longer resets its attempted flag or replaces its measured reason with off-screen or another unmeasured state. Measured mixed-background and shadow-dependent evidence remains visible. Existing scan files are unchanged; rescan to collect corrected measurements.

## Nested text and continuation in 1.12.0

A contrast review on a nested parent is split into rendered DOM text-node runs. Each run uses its own owner element's computed foreground, font threshold, and line rectangles. Direct text before/after child links is included. The original parent passes only if every included run passes; one confirmed failing run fails the parent; unsupported or ambiguous runs keep it unresolved. Up to 80 runs per parent are considered; reaching this limit prevents a parent pass. All temporary style changes are restored, including when several runs share one owner. JSON checks include textRunSummary counts; the attached pixel diagnostics describe a representative run.

When off-screen or scan-limited contrast work remains, **Continue contrast measurements** runs another bounded second-pass batch. It preserves completed results and the original axe counts, refreshes the panel/JSON, and honors the existing auto-save setting. Export JSON if auto-save is disabled. Continuation does not mark unresolved criteria passed or rerun the first-pass axe scan. Navigate or change page states with Scan page to get fresh first-pass evidence.

Unresolved contrast cards are labeled **Contrast measurement gaps — no failure confirmed**, with explanations instead of instructions to change colors. Confirmed failures retain repair guidance.

## Remaining-gap handling in 1.12.0

Contrast measurement no longer requires a background-specific axe reason to attempt an independent passing result. Special/unknown engine cases can pass when the rendered measurement supports it, but cannot become automatic failures solely from that broader eligibility. Engine exception cases stay unresolved when no pass is established. JSON now retains an allowlisted engineReviewCode, mapping unknown strings to other.

Text-node ranges trim surrounding whitespace, and automatic traversal centers the actual run rather than just its potentially oversized owner. This avoids repeated off-screen checks of later inline text and whitespace-only hit-test collisions. Genuine occlusion remains unresolved; exported occlusion metadata records a generic blocker tag/relation without IDs, text, or selectors. Nested textRunSummary includes unresolved reason counts.

One **Continue contrast measurements** action now processes successive batches while they make progress, up to six batches or 90 seconds. It stops on no progress, completion, or user interruption; first-pass evidence and completed results are preserved. The bounded limits still apply and unsupported cases are never silently cleared.

## Link identification in 1.12.0

The second pass now handles link-in-text-block separately from color-contrast. This rule concerns distinguishing links from surrounding non-link text (1.4.1), not readability against the background (1.4.3). Standalone metadata/list links with no rendered surrounding non-link text can resolve through an isolated-link-context assessment. A default underline can resolve when it is distinct from surrounding decoration, uses the text color, is not only a current hover/focus effect, and the same link has a passing text/background check. Generated prose or unsupported context remains unresolved.

For prose links, available CSS colors may be compared with surrounding text using the 3:1 color-only technique threshold. This ratio alone never passes the link-identification review; additional hover/focus cues must be verified. No link-identification failures are inferred by this resolver, and first-pass failures remain unchanged. Exports retain allowlisted linkDistinction context/method/ratio evidence, never link text or addresses. Incomplete cards are labeled as link-identification reviews and use rule-specific guidance.

## Two-pass scan pipeline

Version 1.12.0 runs axe first, then considers every inconclusive element check in a second Access Lens pass. An automatic resolver currently exists for supported text-contrast cases. Other rules receive an explicit no-handler reason; they are never silently dropped or marked passed. Measurement limits, off-screen/obscured text, unsupported CSS or elements, capture failures, page changes, mixed backgrounds, and shadow-dependent results have separate unresolved reasons. Checks needing human judgment and criteria not covered by automated testing remain in the WCAG review catalog.

The panel shows first-pass inconclusive counts and second-pass pass/fail/unresolved counts. Each second-pass finding records its initial axe status, final Access Lens status, whether measurement was attempted, and the reason. JSON includes scanPasses with first-pass bucket counts and second-pass totals, plus per-node secondPass provenance and generic explanations. Existing automated measurements accompany resolved contrast results. Counts describe element checks, not distinct elements or percentages of WCAG compliance.

Resolvers receive copies of the first-pass results. Only originally inconclusive nodes can change categories; existing axe violations, passes, and inapplicable results are preserved. Failed resolvers leave the original reviews intact. Both inspector and browsing scans use this same pipeline. Additional reliable resolvers can be added independently without changing the first-pass engine or treating unsupported checks as passes.

## Automatic image-background contrast

Version 1.12.0 automatically attempts to resolve axe text-contrast reviews caused by images, gradients, pseudo-element overlays, or overlapping layout elements on visible, unobscured leaf text (including wrapped headlines) and standard input buttons. No pixel selection is required. One local viewport capture measures the background with candidate text fill temporarily hidden, then restores the original inline styles. Every line of wrapped text is measured separately with overlays preserved. Text shadows are temporarily suppressed too; shadow-dependent text can pass when the underlying background itself provides sufficient contrast, but is never automatically failed by ignoring its shadow. CSS text colors and normal/large-text thresholds are combined with every captured pixel in the text region. Multiple hit-test points on every text line reject detected occlusion before measurement. A region passes only when all measured ratios meet the threshold; a region fails only when all are below it. Mixed outcomes, unsupported effects, animations/transitions, layout changes, capture denial, off-screen content, and sampling limits remain under manual review. This measures the current rendered state, not all interaction states or full criterion conformance.

The fallback needs an active tab and Chrome capture permission from invoking the extension. It also runs in browsing mode when capture is available; denied/inactive captures leave axe reviews intact. At most 30 candidate elements per viewport are considered; explicit scans can visit additional viewport positions as described above. Screenshots are transient, never saved or exported. JSON checks include automaticBackground with the method, minimum/maximum ratios, and number of sampled pixels. The original axe engine supplies the initial review; the automaticBackground field identifies the extension's additional measurement.

## Rendered contrast sampling

For an unresolved text contrast check, expand its rule in **Contrast** or **Needs review** and choose **Sample rendered background**. The inspector temporarily hides, scrolls the element into view, and captures a cropped image of the visible element. Select a background pixel beside the text, avoiding glyph edges, icons, borders, and shadows. You can also enter a six-digit hexadecimal background color and click **Measure color pair**. The foreground color comes from computed CSS, avoiding antialiasing in screenshot text. The calculation uses the WCAG sRGB relative-luminance formula and the normal/large-text AA threshold without rounding the comparison.

The displayed result applies to that sampled color pair only. Sample multiple points over gradients and images. It never moves an axe review into automated passes or failures, or passes the 1.4.3 checklist. Review applicability, the actual background beneath the text, all states, and font exceptions separately. Position-only transforms (including translateZ(0)) are supported. Empty inputs/placeholders, inactive controls, opacity, blending, scale/rotation/perspective transforms, text shadows/strokes, and unsupported text colors stop this tool with a specific explanation rather than producing a misleading ratio. The full element must fit in the viewport, within 1200 × 600 CSS pixels; large elements and off-screen portions require a separate assessment.

The manual sampler captures after its explicit action in the inspector on an active HTTP/HTTPS page. Automatic scans can also capture for the fallback described above. It uses the existing activeTab grant; if Chrome denies capture, click the extension toolbar button again to restore access. Switching tabs, navigation, viewport changes, or detected element movement invalidates a capture. Browsing scans can use the automatic fallback when the inspected tab is active and Chrome permits capture. A viewport image exists transiently in the worker, and only the element crop is returned to the inspector. Images stay in memory and are never exported, queued, stored, or uploaded. Close the inspector, change views, or use **Clear sample** to discard the displayed crop.

Each selected color pair is exported on the corresponding color-contrast check as renderedSample: CSS foreground color, selected background color, unrounded ratio, threshold, font measurements, measurement method, sample time, and reviewRequired. A selected save folder receives updated evidence; otherwise use **Export JSON**. **Clear sample** removes this evidence too. A new scan starts without earlier samples; reopening a saved report restores manual decisions, not the screenshot or sampling UI.

## Report

Every JSON download uses content-free schema 2.0 across all result categories and inventories. It retains rule IDs, severity, generic rule descriptions, WCAG tags, structural locators, element types, label/alt presence, selected ARIA states, and allowlisted contrast ratios, numeric thresholds, and hexadecimal foreground/background colors, plus versions, timestamp, scope, and counts. The second field, pagePath, contains the scanned page address through its full pathname. It excludes query strings, fragments, and embedded credentials. Page paths can contain identifiers, so handle exports accordingly. Element content remains excluded: HTML, text, page titles, IDs, classes, accessible names, raw check messages/data, and related-node snippets are omitted. Filenames contain only a hashed page identifier. Unresolvable elements have no locator; custom element names use generic structural selectors. Locators may change after DOM updates. There is no full-content export option. Previous downloads are unchanged and may contain sensitive content.

The inspector reads content locally and temporarily holds raw scan data in memory to display findings. Downloads are constructed separately with an explicit field allowlist; raw results are not persisted. Optional comparison history retains only content-free issue baselines and checklist results. Structural information, hashes, and measurements still reveal some page layout and allow reports to be linked; they are not a guarantee of anonymity. Counts describe rules and element occurrences, not unique elements.

Scans run locally, on demand or in explicitly enabled browsing mode. The extension uses `activeTab`, `scripting`, `alarms` for queue retries, and `contextMenus` for the toolbar pause control. Optional host access is requested separately for each browsing-mode site. It does not upload results or automatically grant access to all websites. Rule reference links open external documentation only when clicked.

## Scope and limits

Scans select axe rules mapped to the 55 active WCAG 2.2 Level A/AA criteria, including inherited 2.0/2.1 requirements. Best-practice-only rules, Level AAA rules, and removed criterion 4.1.1 are excluded. Only the rendered top-level document and supported open shadow roots are checked. Embedded frames and closed shadow roots are excluded. Hidden content requires opening it and rescanning. Automated checks cannot establish accessibility or WCAG conformance; manual keyboard, screen reader, and content review remain necessary. This is not WAVE and does not reproduce its proprietary checks or score.

Browser settings, extension stores, and other protected pages block injection. A `!` toolbar badge indicates the page cannot be scanned. Local files require enabling **Allow access to file URLs** in extension settings. Firefox and Safari packaging is not included.
